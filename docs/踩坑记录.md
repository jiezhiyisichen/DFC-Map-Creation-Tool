# 踩坑记录 · 曾经花了很久才解决的 BUG

> 目的：**别再踩第二遍**。这一页收录"编译能过、运行不报错、但功能就是没有"级别的问题，
> 以及排查它们花了半天以上的坑。新功能动手前先扫一眼；解决新坑之后**追加**到这里。
>
> 每条格式：【症状】→【根因】→【修法 / 规则】。更系统的约定在 `.workbuddy/memory/MEMORY.md`。

---

## 1. 显示器 / TESR / GUI 整个不渲染，但日志一个字都没有

- **症状**：方块在、不崩、不报错，画面就是没有（密码盘"不可见"、显示器黑屏、控制台界面空白）。
- **根因**：**ProGuard 把覆写方法改名了**。`-libraryjars` 解析不到运行时的 `net.minecraft.*`，
  它看不出 `render(...)` / `initGui(...)` 是在覆写基类，就把它改名成 `a(...)` 再补一个不覆写的桥接方法。
  Minecraft 调的是基类那个空实现 —— 所以"什么都不执行、什么都不报错"。
- **修法 / 规则**：
  - `tools/proguard.pro` **整包保留 `com.jiezhimod.client.**`**，不要逐个子包列；
  - `run_selftest.py` 从**最终 jar** 反查关键类与覆写方法名（SRG 名）必须还在；
  - 常用 SRG：`func_73866_w_`=initGui、`func_146976_a`=drawGuiContainerBackgroundLayer、
    `func_146284_a`=actionPerformed、`func_73660_a`=update、`func_145839_a`=readFromNBT、
    **`func_189515_b`=writeToNBT**（1.12 起返回 NBTTagCompound，不是 `func_145841_b`）、
    `func_189517_E_`=getUpdateTag、`func_189518_D_`=getUpdatePacket；
  - 排查口诀：**"有个方法就是不执行" → 先反编译产物看方法名还在不在**（`javap -p -cp tools/obf.jar 类名`）。

## 2. 方块实体读档后丢失 / 存档时崩 `missing a mapping!`

- **症状**：区块保存时抛 `xxx is missing a mapping! This is a bug!`；或读档后配置全丢。
- **根因**：`TileEntity` **按具体类**查注册表，不顺着继承链找。父类注册了不等于子类注册了
  （`TileCustomScreen extends TileDfcScreen` 当年就整条漏掉）。
- **修法 / 规则**：每个新的 TileEntity 类都要在 `JiezhiMod.preInit` 里
  `GameRegistry.registerTileEntity(具体类.class, new ResourceLocation(MODID, "名字"))`；
  `run_selftest.py` 会扫源码继承链把所有 TE 类和注册表比对。

## 3. 纯资源改动后进游戏必崩 `integrity check failed`

- **根因**：jar 内置双重完整性校验（SealA/SealB），业务类聚合哈希 H_rest 已固化进 Seal。
  改了任何源码 / 资源（连 mcmod.info 都算）不重跑构建三步就崩。
- **修法 / 规则**：改任何东西都跑全链 ——
  `gradlew build --offline` → ProGuard → `seal_inject.py` → `check_stackmap.py`(OK) → `TestMain`(SEAL OK) → `run_selftest.py`(ALL GREEN)。

## 4. 高级红石中继器"永远不输出红石信号"

- **症状**：输入侧能看到信号、方块也亮，隔壁的灯 / 活塞永远不动。
- **根因**：`FACING` 语义与原版反了（自创"输出侧"），而 `getWeakPower(side)` 的 `side`
  是"**从接收方指向我**"的方向 —— 结果输入和输出挤在同一面。
- **修法 / 规则**：**FACING = 输入侧，输出在 `FACING.getOpposite()`**；
  放置 / 读输入 / 给弱充能 / 锁定四条口径必须**整套**照原版 `BlockRedstoneDiode`，改一处等于整块翻转。
  自测哨兵盯住 `pos.offset(facing.getOpposite())`（出现即报错）。
  查原版行为：`~/.gradle/caches/forge_gradle/minecraft_user_repo/net/minecraftforge/forge/1.12.2-14.23.5.2864/forge-...-patched.jar`
  里有全量 `.java`（SRG 名），直接 unzip 读，比猜快。

## 5. 多块显示器同屏掉帧（"卡一下"）

- **根因**：一次重绘 = 画 768×576 + 抄像素 + 上传 1.7MB，全在渲染线程同步跑；
  几块屏的 200ms 周期撞在同一帧就顶穿帧预算。
- **修法 / 规则**（四处硬约束，改回去就掉帧）：
  1. 像素零拷贝（`DataBufferInt` 直通）；2. 每帧最多重画 2 块（`PAINT_BUDGET` + `beginFrame`）；
  3. 按距离降频；4. **绝不调 `DynamicTexture.updateDynamicTexture()`**（走全局共享 DATA_BUFFER，
  本整合包里失效）—— 自管 direct ByteBuffer + glTexSubImage2D。
- **离线导出工具每帧必须 `ScreenCanvas.beginFrame()`**，否则折线页只画前两点 / 新页面导出空图。

## 6. 离屏导出（canvastest）画出来是空图

- **根因**：同上（被重绘预算拦住），加上**没删旧 class**：改完源码先删 `tools/canvastest/out`，
  旧 class 会盖住 sourcesSets，症状是莫名的 `NoSuchFieldError`。
- 折线页要"**同一个 canvas 连喂 120 次 render**"才有形状，每次 new 一个 canvas 是空图。

## 7. GUI 界面"为什么是 8 条 / 布局错位 / 文字偏半屏"

- **根因**（三个不同的坑，都踩过）：
  1. 激光屏直接套用自定义屏的面板 → 列表按 8 个数据槽画。**子类必须先判**：
     `ScreenMultiblock` / `pageFor` 里先 `TileLaserScreen` 再 `TileCustomScreen`；
  2. GUI 与容器的槽位坐标两处各写一份 → 漂移。坐标常量只留一份，GUI 引用容器的；
  3. 1.12.2 的 `drawGuiContainerBackgroundLayer` **没有 translate**（绝对坐标），
     foreground 层有 translate —— 混着画必偏。约定：**全部画在背景层、用绝对坐标**。
- 版面规矩：面板高 ≤ 240（1.12.2 只保证逻辑分辨率 ≥320×240）、
  提示区必须在按钮 / 背包上方结束 —— 这些都在 SelfTest 里有断言。

## 8. 手持物品时方块右键完全没反应

- **根因**：`Item.onItemUse` 返回 `SUCCESS` 之后，`Block.onBlockActivated` **整个不会执行**。
- **修法 / 规则**：链接器类物品**不蹲下一律返回 `PASS`**，把"开界面"让给方块。
  激光链接器、灯圈链接器都吃过这个亏。

## 9. `mcmod.info` 的版本号 / 占位符不生效

- **根因**：ForgeGradle 3.0 不会替换 `${version}`。
- **修法 / 规则**：mcmod.info **硬编码版本号**，且与 `build.gradle`、`JiezhiMod.VERSION`、
  `tools/proguard.pro`、`tools/seal_inject.py` **五处同步**（+ README 徽章）。

## 10. PowerShell / 编码类

- PowerShell **`&&` 非法**，串联用 `;`；文本读写必须显式 `-Encoding UTF-8`（Python 用 `encoding="utf-8"`）。
- Java 子进程 stdout/stderr 按 **GBK** 解码（`encoding="gbk", errors="replace"`）。
- Git Bash 把 classpath 的 `;` 当分隔符 → 跑 canvastest 必须走 `cmd //c "tools\canvastest\run_dump.bat"`。
- **本机所有 python 默认都没有 Pillow**：`tools/gui_mock/*.py` 需要 →
  `~/.workbuddy/binaries/python/envs/default/Scripts/python.exe -m pip install pillow`（已装）。

## 11. git 提交 / 代理

- **`git commit -m "带引号的中文"` 会被截断** → 提交消息一律 `git commit -F 文件`，
  否则提交失败但 tag 照打，tag 落错 commit。
- `git push` 报 `CONNECT tunnel failed, response 502`：本地代理间歇性抽风 →
  `env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY git -c http.proxy= push origin HEAD`（多试几次）。
- 部署到 mods 目录：**一个实例目录只能留一份同名 jar**，旧的改名 `.jar.bak_<日期>`；
  游戏开着时 jar 被占用 → 放成 `*.jar.new`（FML 不加载非 .jar 后缀），关游戏后手动换。

## 12. 红石类方块的通用坑

- **红石变化通知路径很碎**（neighborChanged / 强弱充能 / 比较器各一套）：
  控制台类一律**每 5 tick 轮询 + 上升沿检测**，不要监听事件。
- 要**记住输出状态**（下降沿少 1 刻的坑）：中继器/控制台的输出由自己存，不要从计数器反推。
- **步进按钮必须从输入框累加**（从"已生效值"累加会让第二下回到原点）。

## 13. 灯圈（v4.4）的"着色器"选型

- **不要自写 GLSL**：OptiFine / Iris 会整体接管渲染，装上光影自写 shader 直接失效。
- 用**原版 tint 管线**（`tintindex` + `IBlockColor`）—— 所有光影包都尊重它；
  发光用 `getLightValue`（亮时 15），方块自身全亮、周围被照亮。
- tint 只在**烘焙**时采样 → 渐变期间客户端要节流地 `markBlockRangeForRenderUpdate`（每 2 刻）。
- 颜色/亮灭是**参数快照 + 客户端本地插值**（`RingState`），不要逐刻发包；
  时钟对齐用"收到快照时的本地刻"，不要直接比服务端 / 客户端的世界时间。
- ★ **翻方块状态会引爆邻居回调**：`World#setBlockState` 会把 6 个邻居的 `neighborChanged`
  全叫一遍。一组 N 格灯带同时亮/灭 = N 次 setBlockState → 最多 6N 次回调 →
  每次又做一遍 O(N) 洪水填充。N=60 闪一次就是几万次分配，实机表现"灯圈一闪，画面顿一下"。
  翻自己的状态**不改变成员关系**，所以要用静默期挡掉（`RingGroupManager.beginQuiet/endQuiet`
  + `neighborChanged` 里 `if (quiet()) return;`）。凡是"状态变化会连带触发结构重建"的方块，
  都要问一遍：这个重建是不是白做的？

## 14. 一进游戏就崩：`NPE at ClientProxy.onModelRegistry`（v4.4 实测）

- **症状**：启动到 preInit 阶段直接崩，`java.lang.NullPointerException` 栈顶就是
  `com.jiezhimod.proxy.ClientProxy.onModelRegistry`，没有任何下层帧 —— 说明是"在那一行取到 null 又直接用了"。
- **根因**：我在 `ModelRegistryEvent` 里注册方块颜色
  （`Minecraft.getMinecraft().getBlockColors().registerBlockColorHandler(...)`）。
  但原版 `Minecraft` 的构造顺序是：
  ```
  第 378 行  this.init();        // 里面 preInit → ModelRegistryEvent
  第 514 行  this.blockColors = BlockColors.create();
  第 515 行  this.itemColors  = ItemColors.create(blockColors);
  ```
  **ModelRegistryEvent 触发时两个颜色表都还是 null**。
- **修法 / 规则**：颜色必须挂在 Forge 的 **`ColorHandlerEvent.Block` / `ColorHandlerEvent.Item`**
  （资源加载阶段、颜色表就绪之后触发），并把处理器注册到 `MinecraftForge.EVENT_BUS`
  （不是 @Mod 总线）。见 `com.jiezhimod.client.ring.RingColorHandlers` +
  `ClientProxy.init()` 里的注册。
- **哨兵**：`run_selftest.py` 现在会把 `onModelRegistry` 的方法体抠出来，
  里面出现 `getBlockColors` / `getItemColors` / `registerBlockColorHandler` 就报错。
  （扫之前**先剥掉注释** —— 这段坑本身就得在源码注释里解释，不剥会把说明文字当成违规调用。）
- **同类提醒**：`Minecraft.getMinecraft()` 自己在 preInit 阶段也可能还没就绪 ——
  凡是 `Minecraft` 上的东西（颜色表、`effectRenderer`、`renderItem`…），
  一律不要放在 `ModelRegistryEvent` / `preInit` 里取。

## 15. 方块实体"运行期改了状态，客户端毫无反应"（v4.4 实测，灯圈一直白色）

- **症状**：控制台点了"换成红色"、服务端日志也打了"应用到 N 格"，但游戏里灯圈**始终是白的**，
  重启存档后再看颜色也还是白的（因为颜色根本没存进客户端，服务端 NBT 有）。
- **根因**：以为改了状态 + `world.notifyBlockUpdate(pos, st, st, 3)` 就会同步方块实体。**不会**：
  - `World.notifyBlockUpdate` 只是转给 `IWorldEventListener`，服务端最终发的是
    **`SPacketBlockChange` —— 只带方块状态（state id），不带方块实体 NBT**；
  - `SPacketUpdateTileEntity`（来自 `getUpdatePacket()`）只在**区块加载**时随
    `SPacketChunkData` 发一次，运行期没有任何人替你发。
  - ⇒ 客户端方块实体的 `recvTickSet` 永远是 false，客户端算出来的颜色停在默认白。
- **修法 / 规则**：**运行期的方块实体状态必须自己发包。**
  本项目里 DFC 显示器一直是这么做的（`MessageDfcScreen`），灯圈照抄：
  `MessageRingState`（服务端 → 客户端，带组快照 + 成员坐标，每包 256 格）
  + `RingNet.broadcast`（半径 96），在**状态真的变了**才发（`setState` 返回 false 就闭嘴，
  免得红石粉抖一下全组刷一遍）。
- **客户端落地**：`TileLightRing.applySync(state, clientNow)` 里重置插值进度、记下"收到时的本地刻"、
  立刻 `markBlockRangeForRenderUpdate`（tint 只在烘焙时采样，不刷就没有新颜色）。
- **另一条容易忘的**：客户端算出来的颜色只是"渲染用"，**发光强度走的是方块属性
  `POWERED`**，那个必须在服务端用 `setBlockState(..., 3)` 翻，否则灯亮着但不发光。

## 16. 槽位"拒绝"是会静默失败的（v4.4 实测：激光链接器放不进去）

- **症状**：玩家把激光链接器拖进一个显示器的槽位，物品**弹回原位**，界面/聊天栏
  一个字都没有 —— 玩家立刻判定"这模组坏了"。
- **真相**：`Slot#isItemValid()` 返回 false 时，原版 `Container#slotClick` 就是
  **什么都不做、什么都不说**。设计上没错（那块是自定义显示屏，只收 DFC 遥控器），
  但"沉默的拒绝"和"bug"在玩家眼里长得一模一样。
- **规则**：任何**按类型过滤**的槽位（遥控器槽 / 链接器槽 / 只收某物品的槽），
  都必须补一条"为什么不行"的反馈。两种一起上最省事：
  1. 容器里覆写 `slotClick` + `transferStackInSlot`：被拒时 `player.sendStatusMessage(...)`，
     **同一刻只提示一次**（连点会刷屏）。
     ★ 一定要**先调 `super` 再补提示**，绝不能拦在前面 `return ItemStack.EMPTY` ——
     那会把玩家光标上拿着的那叠物品直接弄没。
  2. GUI 侧：检测到"手持/光标上拿着的东西不该放这里"时，把底部提示**换成橙色指引**，
     玩家不用点就知道该去哪。
- **同类坑（同一个根因的另一面）**：子类屏被路由成父类面板。`TileLaserScreen extends
  TileCustomScreen`，只要有一条路径用了 `instanceof TileCustomScreen` 就打开 8 行面板，
  而那个面板的槽位只收遥控器 —— 于是又回到上面那个"静默拒绝"。
  修法是**两份 Proxy 的 `GUI_CUSTOM_SCREEN` 分支里都先判 `TileLaserScreen`**，
  而且**判据必须完全一致**：客户端和服务端各判一套、结果不同，就是槽位错位 / 物品消失。

## 17. 方块实体"看着对、其实不是这个类"（v4.4 实机，损失了整块激光屏）

- **症状**：屏幕画面完全正常（画的是新那一页、标题对、提示对），但**面板是父类那一套**：
  行数不对、槽位只收父类的物品、子类的配置/读数永远不生效。
  本项目里的具体表现是：激光状态显示器画着"激光状态 0/4"，右键却弹出自定义屏的 8 行面板，
  激光链接器拖不进去。
- **根因（记住这一条就够了）**：**1.12.2 实际调用的是 `Block.createTileEntity(World, IBlockState)`**。
  `createNewTileEntity` 只是 `BlockContainer.createTileEntity` 的**默认实现**内部才会去调。
  一旦某个祖先覆写了 `createTileEntity`（本项目 `BlockDfcScreen` 就覆写了并直接返回
  `new TileDfcScreen()`），子类只写 `createNewTileEntity` = **永远不生效**，而且**毫无报错**。
- **为什么难发现**：选页 / 渲染是按**方块类型**判的（`ScreenLayout.pageFor`），
  所以画面永远是对的；错的只有"面板 + 数据"，看起来像"按钮坏了"。
- **排查法**：在那块屏的位置上把方块实体类打出来
  （`world.getTileEntity(pos).getClass()`），一眼就能看出是不是你写的那个类。
- **修法**：子类**两个方法都覆写**；并给旧存档做迁移 ——
  原版 `TileEntity.create` 是**按 NBT 的 `id` 造类**的（不是按方块），
  所以光修创建入口只能救新放的方块。迁移写在 `onLoad` + `update` 里：
  比对`desiredTileFor(block)` 与实际类，不一致就搬 NBT → `invalidate()` 旧的 →
  `World.setTileEntity` 换新的；整段 `try/catch`，**绝不能让迁移失败变成区块加载失败**。
- **哨兵**：`run_selftest.py` 会顺着继承链检查 ——
  "祖先覆写了 `createTileEntity`、自己却只写 `createNewTileEntity`" 直接报错。
  这条哨兵当初就顺手抓出了**标注显示器（v4.1 起）也是同一个坑**。

## 18. "兜底"逻辑把正经逻辑踩掉（v4.4 中继器延时失效）

- **症状**：中继器设了 5 秒延时，第一次好像生效，之后每次触发都立刻通 ——
  玩家描述成"设好的延时记不住、用一次就回到默认"。
- **根因**：`neighborChanged` 里给长延时排了一个 `scheduleUpdate(pos, this, delay)`
  当保险（怕计数器没在跑）；而 `recompute(fromSchedule=true)` 里写的是
  `if (input != output) timer.syncOutput(input)` —— **无条件对齐**。
  计划刻是每次邻居变化都排一次，经常在延时还没走完就到点，于是直接跳过延时。
  ⇒ **"兜底"必须能证明"该兜"，否则它会变成一条绕过主逻辑的近路。**
- **规则**：兜底分支里先判断"主逻辑是不是真的没在跑"，例如
  `timer.elapsed() >= delay - 1`（确实等满了才强制对齐），否则照常推进。
- **同一个坑的另一半**：`readFromNBT` 里 `clamp(getInteger(KEY))` —— 缺键时
  `getInteger` 返回 **0**，`clamp(0)` 得到的是最小值而不是默认值，
  于是"某个只带部分字段的 NBT"就把玩家设置悄悄改成最小。缺键要先 `hasKey`。

## 19. 每次都在"配置没到客户端"上翻车（v4.4 灯圈控制台）

- 这个项目里 `world.notifyBlockUpdate(pos, state, state, n)` **不等于**同步方块实体。
  它最终只发 `SPacketBlockChange`（只带方块状态）；`SPacketUpdateTileEntity`
  只在**区块加载**时随 `SPacketChunkData` 发一次。
- 于是凡是"服务端存了配置、界面要读回来"的东西（显示器配置、灯圈控制台配置…），
  都必须**自己发包**。已经踩过三次：DFC 自定义屏、灯圈组状态、灯圈控制台。
- **自检口诀**：写完 `xxxConfig.apply(...)` 之后问一句
  "客户端下一次打开界面，这些值从哪来？" 答不上来就是漏了一个包。
- 灯圈控制台的具体后果：重开界面全是默认值 → 再按一次「应用」→
  用默认值把服务端那份好配置**覆盖掉**（表现为"怎么配都不生效"）。

## 20. 注册监听器"时机对"还不够，得看**事件什么时候发**（v4.4 灯圈永不变色）

- **症状**：服务端日志明明白白 `[Ring] broadcast … color=#FF3A3A`，客户端也 `sync -> #FF3A3A`，
  但灯圈**永远是白的**，渐变 / 闪烁淡入淡出全部看不到。
- **根因**：颜色处理器用 `ColorHandlerEvent.Block` 注册（事件本身选对了），
  但**注册监听器的代码写在 `@Mod.EventHandler init()` 里**。
  原版 `Minecraft` 构造顺序（对着 patched 源码数的）：
  ```
  467  beginMinecraftLoading → loadMods → preinitializeMods   ⇒ 模组 preInit
  514  BlockColors.create()  → 内部 post ColorHandlerEvent.Block
  515  ItemColors.create()   → 内部 post ColorHandlerEvent.Item
  535  finishMinecraftLoading → initializeMods                ⇒ 模组 init
  ```
  ⇒ **颜色事件在 init 之前就发完了**，监听器加进总线时事件已经过去。
  `IBlockColor` 没注册上，渲染层就当"这个方块没有颜色倍率"，贴图原样显示。
- **规则**：凡是"只在启动阶段发一次"的 Forge 事件（`ColorHandlerEvent`、
  `ModelRegistryEvent`、`RegistryEvent`…），**监听器必须在 preInit 里就挂好**。
  判断方法：去 `Minecraft.java` 里找那个事件的 post 点在第几行，再跟 467/535 比。
- **哨兵**：`run_selftest.py` 检查 `RingColorHandlers()` 必须出现在
  `preInit()` 与 `init()` 之间。

## 21. 方块模型的 `faces.texture` 只接受 `#变量`（v4.4 中继器变紫黑格）

- 症状：方块整个变成紫黑棋盘格（玩家口中的"乱码"）。
- 根因：模型 JSON 里写 `"texture": "minecraft:blocks/redstone_torch_on"`。
  `ModelBlock.resolveTextureName()` 会先看这个名字**在 `textures` 表里有没有**，
  没有就当成变量名补一个 `#` 再去查 → 查不到 → 整个模型加载失败 → 紫黑格。
- 规则：`faces.<面>.texture` **永远写 `#名字`**，真实资源路径只写在 `textures` 里。
  自测哨兵会扫 8 个中继器模型的所有面。

## 22. blockstates 的 variant key，属性顺序必须按**属性名字母序**（v4.4 中继器"仍"紫黑格）

- 症状：模型文件明明没问题（面贴图都是 `#变量`、变量也都定义了），方块还是紫黑棋盘格。
- 铁证在日志里：
  ```
  Exception loading model for variant jiezhimod:advanced_repeater#facing=east,input=false,locked=true,powered=false
  Caused by: net.minecraft.client.renderer.block.model.ModelBlockDefinition$MissingVariantException
  ```
- 根因：`BlockStateContainer` 构造时把属性**按名字排序**存进 `propertiesList`，
  `ModelResourceLocation` 的 variant 字符串就是照这个顺序拼的
  （`facing=east,input=false,locked=true,powered=false`）；
  而 `Blockstates` 的 key 在 `ModelBlockDefinition.Deserializer` 里是**原样字符串直接放 Map**，
  匹配时拿拼好的字符串去 `get()`。顺序不一致 ⇒ 查不到 ⇒ `MissingVariantException`。
- 隐蔽点：**只有三个属性时 `facing < locked < powered` 恰好就是字母序**，
  所以老版本怎么写都对；一加 `input`，正确顺序变成 `facing,input,locked,powered`，
  生成脚本还按老顺序拼，就全崩了 —— 而且不是"全崩"，是懒加载到哪个变体就报哪个，看着像"部分缺失"。
- 规则：blockstates 的 key 一律按属性名字母序写（`facing,input,locked,powered`）。
  自测哨兵逐个 key 解析属性名比对 `sorted()`，别用子串匹配（会被书写顺序绑死）。

## 23. `IBlockColor` 的 tint 只在**区块重烘焙**时采样 —— 动态亮度必须走方块状态（v4.4 灯圈闪烁无效）

- 症状：灯圈颜色能切换（因为切颜色时会主动请求一次重烘焙），但**闪烁 / 淡入淡出**画面完全不动；
  日志证明包到了、客户端也算出了 `#2C2C2D` 这种灭态色，就是不变。
- 根因两层：
  1. 顶点颜色是烘焙时乘进 `BufferBuilder` 的，渲染每一帧**不会**重新问 `IBlockColor`。
     所以"颜色每刻在变"和"画面每刻在变"是两件事。
  2. 更隐蔽：`displayColor()` 里既读又写 `this.displayColor`。它被 tint 调用（= 烘焙那一刻）
     写回一次，`clientTick` 下一 tick 比对"颜色没变"就 `return`，**再也不会请求重烘焙** ——
     自己把自己锁死在某一帧。
- 规则：
  - **想每帧/每刻变的东西，放进方块状态**（`PropertyInteger` 档位），
    改状态会同时触发重烘焙 + 光照重算，两条路一起走，且比你手动 `markBlockRangeForRenderUpdate` 可靠。
  - 写方块状态的时机是"**档位真的变了**"，不要每刻无脑写（那才是卡顿来源）。
  - tint getter **只读**。任何"顺手把字段更新一下"的写法都会把调用方的"变了没有"判据废掉。
  - 灯圈 meta 只有 1 bit 在用，`PropertyInteger(0,15)` 正好塞满 4 bit —— 做"多档亮度"前先数 meta 余量。

## 24. 「告警灯」必须独占控制通道，否则告警色刚亮就被刷回去（v4.5 警示灯联动）

- 症状（设计阶段就能预见，实测确认）：警示灯接上显示屏之后，控制台每次红石沿都会
  把「统一颜色 + 开关」推给成员表里的所有灯，告警刚变红立刻被推回原来的红色常亮，
  甚至变成"关"。玩家看到的现象是"联动好像生效了一瞬间"。
- 根因：**同一盏灯被两套逻辑写**。控制台是"广播式写"，告警是"状态式写"，
  两个写者没有优先级，谁后到算谁。
- 规则：
  - 一个执行器只能有一个"权威写者"。接显示屏的灯，`applyConsoleConfig()` 里判
    `isAuto()` 直接 return；控制台**必须**走这个入口，不能直接调 `applyConfig`。
  - 玩家显式改绑（用链接器重新绑控制台）时才 `clearSource()` 交回手动 —— 别自动抢。
  - 手动操作（染料刷色）在联动状态下要**明确拒绝并说明原因**，否则玩家会以为染料坏了。
  - 自测哨兵盯 `TileAlarmConsole` 里出现的是 `applyConsoleConfig` 而不是 `applyConfig`。

## 25. 告警阈值要"两个条件"筛，不然会误报（v4.5 稳定度）

- 症状：自测里一份很普通的快照（温度 1000°C、无稳定器）被判成"危急（橙）"。
- 根因：稳定度只看 `online()`（温度 ≥ 100°C）。但 `stabilization` 是**累加值**，
  刚点着的核心还是 0、停堆时也不掉回 0 —— 前者误报、后者一直报。
- 规则：判"稳定度不足"必须 `online() && stabilizers > 0 && stabilization > 0`。
  凡是"累加型"指标，都要先确认它**有在攒**再判好坏。
- 附带经验：把告警映射抽成纯函数（`AlertRules`）之后，这类误报在离线自测里就暴露了；
  写在 `TileEntity.update()` 里的话，只能进游戏一格一格配色去试。
